### Технический радар 

Для визуализации текущего состояния технологий и планируемых изменений составлен **технический радар**. В виде таблицы ниже перечислены основные используемые технологии/методологии, их текущее состояние, а также предлагаемые изменения (что будет введено или обновлено) в целевой архитектуре:

| **Категория**              | **Текущее состояние**                                                                                                                                                        | **Предлагаемые изменения (через год)**                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Архитектура**            | *Монолитная/сложно связанная*. Новая функциональность иногда добавляется в виде SQL-скриптов и процедур в DWH. Выпуски редкие, блокирующие.                                  | **Микросервисная, событийно-ориентированная**. Полное выделение сервисов по доменам, взаимодействие через REST и события. Это повысит гибкость и скорость изменений.                                                                                                                                                                                                                                                                                                           |
| **Domain Design**          | *Отсутствует явный DDD*. Границы контекстов размыты, логика смешана.                                                                                                         | **Domain-Driven Design (DDD)**. Введены четкие bounded contexts, согласованные с бизнес-доменами. Модель каждого контекста автономна. Контексты взаимодействуют явно через API/Events.                                                                                                                                                                                                                                                                                         |
| **Data Warehouse**         | *MS SQL Server 2008*. Основное корпоративное хранилище, но устаревшее, на грани поддержки. Часто выступает инструментом не только отчётности, но и “склеивания” данных.      | **Современный DWH/ Data Lake**. Обновление до SQL Server 2019+ или миграция в облачный DWH (например, Azure Synapse). DWH используется **только для BI**, заполнение через потоковые и пакетные загрузки из микросервисов.                                                                                                                                                                                                                                                     |
| **Базы данных в доменах**  | *Общий подход:* монолитная БД или несколько связанных БД. Медицинские и финданные потенциально могут находиться в одних хранилищах.                                          | **Изоляция баз данных каждого микросервиса** (финансовые сервисы – своя БД, мед – своя, и т.д.). Выбор типа БД под задачу: реляционные для транзакций (PostgreSQL/MySQL или обновленный MS SQL), NoSQL для некоторых сервисов (если нужны масштабируемость/ключ-значение хранилища). Обеспечение **полной ответственности** сервиса за свои данные (без прямых чужих запросов).                                                                                                |
| **Integration (ESB)**      | *Apache Camel* как шина интеграции. Используется повсеместно для маршрутизации данных между компонентами, к DWH, к внешним системам. Централизован, может быть узким местом. | **Event Streaming + Smart Endpoints.** Вводится **Kafka** (или аналог) как распределенная шина событий для коммуникации между микросервисами – позволяя полностью декаплировать их. Camel трансформируется в вспомогательный ETL-инструмент и средство интеграции с legacy (если нужно). Больше не является единой точкой коммуникации.                                                                                                                                        |
| **API Gateway**            | *Отсутствует/ограничен*. Возможно, сейчас клиенты обращаются к нескольким точкам или через примитивный реверс-прокси.                                                        | **API Gateway** паттерн внедряется (например, на базе NGINX, Kong, Tyk). Единая точка входа для внешних запросов, маршрутизация к нужным микросервисам, выполнение общей логики (аутентификация, троттлинг). Повышает безопасность и упрощает внешнюю интеграцию.                                                                                                                                                                                                              |
| **DevOps & CI/CD**         | *Традиционный подход*. Развертывание вручную на серверах, длинные релизные циклы. Автотесты и CI ограничены.                                                                 | **Полноценный CI/CD.** Настройка конвейеров (GitLab CI/Jenkins) для сборки, тестирования и деплоя каждого микросервиса. **Непрерывная доставка** изменений небольшими порциями. Infrastructure as Code (Terraform/Ansible) для воспроизводимости окружений.                                                                                                                                                                                                                    |
| **Containerization**       | *Ограниченно.* Возможно, используются VM или даже физические сервера. Нет унифицированного контейнерного окружения.                                                          | **Docker + Kubernetes.** Все новые микросервисы упакованы в контейнеры Docker. Развертывание в кластер Kubernetes (он-прем или в облаке) для автоматического скейлинга, управления отказоустойчивостью. Это облегчит управление десятками сервисов.                                                                                                                                                                                                                            |
| **Observability**          | *Фрагментарно.* Логирование разрозненно по системам, мониторинг базовый (на уровне инфраструктуры).                                                                          | **Централизованный мониторинг.** Внедрение ELK/EFK-стека для логов, Prometheus + Grafana для метрик. Трассировка запросов между микросервисами (Distributed Tracing, например Jaeger) для быстрого поиска проблем. Это критично в распределенной системе.                                                                                                                                                                                                                      |
| **Security & Compliance**  | *Базовый.* Авторизация/аутентификация возможно встроена в монолит. Контроль доступа к данным на уровне SQL. Соблюдение HIPAA/GDPR требует ручного контроля.                  | **Безопасность по периметру и данным.** Единый сервис аутентификации (SSO, OAuth2) для всех API через гейтвей. Гранулярная авторизация на уровне микросервисов (JWT токены с ролями). **Анонимизация данных** в потоках аналитики (средствами доменов). Логирование доступа к чувствительным данным для аудита.                                                                                                                                                                |
| **BI & Analytics**         | *Power BI, статические витрины.* Отчеты формируются на основе данных DWH, обновление данных – раз в сутки или по расписанию. Ограниченная интерактивность.                   | **Оперативная аналитика.** Переход на **почти реальное время** для ключевых метрик: использование стриминга (Kafka Connect, Spark Streaming) чтобы обновлять витрины быстрее. Power BI остается основным инструментом для конечных пользователей, но получает данные с минимальной задержкой (например, несколько минут). Также рассматривается внедрение **Data Science** платформы для продвинутой аналитики на обезличенных данных (Databricks, Jupyterhub для аналитиков). |
| **AI/ML**                  | *Отдельные скрипты/сервисы*. Модели обучаются вручную, результаты интегрируются точечно (может, через выгрузки). Нет MLops.                                                  | **AI-сервисы как часть архитектуры.** Развертывание моделей в виде API-сервисов (Docker/TF Serving). Модели регулярно переобучаются на обновленных данных из доменов. Внедрение MLops-подхода: мониторинг качества моделей, автоматизация обучения. AI становится **полноправным доменом**, поставляющим ценность в реальные процессы (напр. автоматическое решение кредитов, диагностика по снимкам и пр.).                                                                   |
| **Методологии разработки** | *Традиционные (возможно, Waterfall или местечковый Agile).* Команды связаны монолитом, границы ответственности нечеткие.                                                     | **Agile/Scrum + DevOps culture.** Кросс-функциональные продуктовые команды по доменам. Короткие спринты, непрерывное улучшение. DevOps-менталитет: разработчики несут ответственность за работу сервиса в продакшене (т.е. настроен мониторинг, алерты, on-call дежурства). Это ускорит выявление и решение проблем и повысит качество.                                                                                                                                        |

**Радар показывает, что из текущего стека остается, а что добавляется.** 
* Power BI остается (технология в секторе *Adopt/Hold* – мы продолжаем активно использовать), 
* Apache Camel переходит в сектор *Assess* (т.е. используется ограниченно, оцениваем возможность замены), 
* Kafka, Kubernetes, DDD – новые технологии/подходы, которые находятся в секторах *Trial/Adopt* (пробуем и планируем активно внедрять). 
* Устаревшие технологии (MS SQL 2008, монолитный подход) переходят в сектор *Hold/Drop* – от них планируем отказаться.
